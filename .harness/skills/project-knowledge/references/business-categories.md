# Business Categories

选择 business/domain、business/rules 或 business/processes 时读取本参考。
### 6.1 business/domain

**核心问题**

这个业务世界中有什么对象、概念、角色和术语，它们的业务含义和关系是什么？

**收录范围**

- 业务对象、聚合概念和稳定业务实体；
- 业务术语、同义词、缩写和术语边界；
- 参与业务的角色及其职责含义；
- 对象之间的业务关系、归属和基数；
- 生命周期阶段的基本概念，但不展开状态转换条件和执行步骤；
- 跨产品或跨模块仍保持稳定的领域定义。

**排除范围**

- 创建、审批、支付、退款等端到端步骤，进入 business/processes；
- 是否允许、何时失败、状态能否转换等条件，进入 business/rules；
- 数据库表、字段、索引和持久化关系，进入 technical/data；
- Entity、Service、Controller 等代码实现，进入 technical/modules；
- API 请求和响应，进入 technical/interfaces。

**判断规则**

满足以下条件时选择本分类：

1. Primary question 可以改写为“X 是什么”“X 与 Y 在业务上是什么关系”或“角色 Z 的业务含义是什么”；
2. 删除所有代码、数据库和部署细节后，主要结论仍成立；
3. 文章的中心是定义和关系，不是条件判断或时间顺序。

文章应优先包含：定义、适用范围、关键属性的业务含义、相关角色、业务关系、易混淆术语和生命周期概览。

**典型文章**

- 投资者、基金账户与交易账户的业务关系
- 订单、订单项与履约单术语说明
- 商户、门店与操作员角色模型
- 基金份额与可用份额的概念边界
- 退款、撤销与冲正的业务含义

**相邻分类区别**

- 与 rules：domain 定义“是什么”；rules 判断“什么条件下允许或变化”。
- 与 processes：domain 描述稳定对象和关系；processes 描述事件如何按时间推进。
- 与 data：domain 是业务语义；data 是系统中的数据表达、存储和一致性。

### 6.2 business/rules

**核心问题**

什么条件下允许、禁止、成功、失败，或允许某个业务状态发生变化？

**收录范围**

- 业务校验、资格和准入条件；
- 状态约束和状态转换条件；
- 金额、数量、时间、次数等业务阈值；
- 业务幂等和重复操作判定；
- 业务权限和角色可执行条件；
- 成功、失败、拒绝、失效和过期判定；
- 规则优先级、例外条件和适用范围。

**排除范围**

- 从触发到完成的完整步骤，进入 business/processes；
- 单纯定义状态或对象含义，进入 business/domain；
- 参数格式、HTTP 状态码和接口错误契约，进入 technical/interfaces；
- if/else、规则引擎类和代码实现细节，进入 technical/modules；
- 未经来源确认的合理建议或通用业务经验。

**判断规则**

满足以下条件时选择本分类：

1. Primary question 以“什么情况下”“是否可以”“满足哪些条件”“何时判定失败”表达；
2. 主要产出可以写成条件、约束、决策表或状态转换守卫；
3. 去掉执行步骤后，文章仍能完整回答主要问题。

文章应优先包含：适用对象、前置条件、允许与禁止条件、结果、例外、优先级、状态转换表和来源。

**典型文章**

- 基金申购资格与限额规则
- 订单取消允许条件
- 交易失败判定规则
- 支付请求幂等判定
- 账户冻结与解冻条件

**相邻分类区别**

- 与 domain：domain 定义状态和对象；rules 定义这些状态何时可进入、退出或判定。
- 与 processes：rules 是决策条件；processes 是端到端时间顺序。流程中引用规则时链接规则文章，不复制完整规则集。
- 与 standards：rules 约束业务行为；standards 约束团队如何设计、编码、测试或运维。

### 6.3 business/processes

**核心问题**

一个业务事件从触发到结束如何发生，参与者按什么顺序协作，正常和异常路径产生什么结果？

**收录范围**

- 端到端业务流程和业务场景；
- 触发事件、参与角色、前置和结束条件；
- 业务步骤及顺序、分支和等待点；
- 流程中的业务状态变化；
- 正常路径、异常路径、补偿路径和最终结果；
- 跨系统步骤，但只描述理解业务流程所需的技术触点。

**排除范围**

- 单独的允许或禁止条件，进入 business/rules；
- 单独的业务对象定义，进入 business/domain；
- 服务内部方法调用和代码执行链，进入 technical/modules；
- 系统级组件依赖图，进入 technical/architecture；
- 面向调用方的字段和错误码，进入 technical/interfaces；
- 故障排查和恢复 Runbook，进入 technical/operations。

**判断规则**

满足以下条件时选择本分类：

1. Primary question 是“业务如何从开始走到结束”；
2. 时间顺序、参与者、分支和结果是文章不可删除的主体；
3. 即使提到 API、Service、DB、MQ，技术元素也只是业务步骤的承载者。

文章应优先包含：目标、触发、参与者、前置条件、编号步骤、状态变化、正常路径、异常或补偿路径、结束状态和相关规则链接。

**典型文章**

- 投资者开户流程
- 基金申购处理流程
- 订单创建与履约流程
- 退款与资金退回流程
- 交易异常补偿流程

**相邻分类区别**

- 与 rules：processes 描述“先后怎么走”；rules 描述“某一步能否继续”。
- 与 modules：processes 用业务语言组织参与者和结果；modules 用代码边界组织内部实现。
- 与 architecture：processes 可以展示一条具体业务链路；architecture 解释系统整体边界和组件关系。
