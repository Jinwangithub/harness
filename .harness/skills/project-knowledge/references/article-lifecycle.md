# Article Lifecycle

判断 wiki 文章粒度、拆分/合并、New/Update/Disputed/No material 或正文覆盖范围时读取本参考。
## 9. 文章粒度与动作判定

### 9.1 一篇文章只回答一个主要问题

推荐粒度：

- 一个稳定业务概念；
- 一组围绕同一决策目标的稳定业务规则；
- 一个端到端业务流程；
- 一个稳定技术模块；
- 一个面向同一调用场景的接口集合；
- 一个稳定数据模型或数据流；
- 一个基础设施主题；
- 一个可复用运维问题或 Runbook；
- 一项已经确认的工程规范。

不推荐：

- 整个项目一篇文章；
- 一个 Java 类一篇文章；
- 一份来源文档机械生成一篇同名 wiki；
- 把业务流程、API、代码实现、数据模型和运维全部合并成“全链路大全”；
- 为追求短小把同一主要问题拆成多个无法独立理解的碎片。

### 9.2 拆分判定

出现任一情况时拆分：

- 草稿有两个可以独立表达的 Primary question；
- 两部分面向不同读者任务；
- 两部分由不同来源和维护责任支撑；
- 一部分变化时，另一部分通常不需要一起更新；
- 文章横跨两个分类，且次要部分不是理解主要问题所必需。

拆分后用 See Also 建立关系，不复制正文。

### 9.3 合并判定

只有同时满足以下条件时合并：

- 主要问题相同；
- 读者需要同时理解这些事实才能完成同一任务；
- 证据、适用范围和维护周期基本一致；
- 合并不会让文章跨分类或产生多个独立结论中心。

### 9.4 New、Update、Disputed、No material

- New：没有文章回答同一 Primary question，且候选形成稳定知识。
- Update：已有文章回答同一 Primary question，新来源补充、修正或改变核心结论。
- Disputed：多个可靠来源对同一结论不一致，无法依据权威性或时效明确取代。
- No material：来源值得保存，但没有新增、改变或否定长期知识。只写 raw 和 log。

相同主题更新原文，不创建 -v2、-new、-final 副本。新来源明确替代旧结论时保留有历史价值的旧内容并标记 Outdated。

## 13. 分类文章的主体内容要求

| 分类 | 主体至少应覆盖 |
|---|---|
| business/domain | 定义、关系、角色、术语边界、生命周期概览 |
| business/rules | 适用对象、条件、结果、例外、优先级、状态守卫 |
| business/processes | 触发、参与者、步骤、分支、状态变化、异常和结果 |
| technical/architecture | 系统上下文、边界、组件关系、关键链路、系统级约束 |
| technical/modules | 职责、代码位置、入口、内部协作、实现、扩展点、测试定位 |
| technical/interfaces | 调用者、协议、请求、响应、错误、超时、幂等、版本和兼容性 |
| technical/data | 模型、所有者、关系、存储、流转、生命周期、一致性和缓存语义 |
| technical/infrastructure | 依赖、环境、拓扑、版本、配置来源、连接、容量和安全边界 |
| technical/operations | 现象、影响、观察点、排查、恢复、回滚、验证和升级路径 |
| technical/standards | 规则、适用范围、确认依据、强制性、正反例、例外和检查方式 |

这是内容检查表，不是要求每篇文章机械生成所有标题。没有来源支持的部分应省略或写 Open question。
